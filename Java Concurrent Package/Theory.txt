java.util.concurrent Package in Java:
-> In multi-threaded applications, multiple threads often need to access and modify shared data structures
like lists, maps, and sets. If not handled properly, this can lead to data inconsistency, poor performance,
 or runtime errors.
-> To address these challenges, Java introduced the java.util.concurrent package in JDK 1.5,
 providing high-performance, thread-safe collections and utilities designed for concurrent environments.

Problems with Traditional Collections:
a) Not Thread-Safe
->Traditional collection classes like ArrayList, HashMap, HashSet, etc., are not thread-safe.
This means:If multiple threads access and modify these collections simultaneously,
There can be data corruption or inconsistent results.
Example:
List<Integer> list = new ArrayList<>();
// If two threads add/remove elements at the same time -> data inconsistency!
So, traditional collections are unsafe for multi-threaded environments.

b) Old Thread-Safe Collections Are Too Slow
-> Before Java 1.5, Java provided some synchronized collections, such as:
Vector (thread-safe version of ArrayList)
Hashtable (thread-safe version of HashMap)
Collections.synchronizedList(list)
Collections.synchronizedSet(set)
Collections.synchronizedMap(map)
These classes are technically thread-safe, but performance-wise they are poor.
Why?
Because:
-> Every operation (add, get, remove, even contains) is synchronized.That means only one thread can access
the entire collection at a time.Even simple read operations block other threads.
This causes:
High waiting time for threads,
Reduced concurrency,
Poor scalability on multi-core systems.

Example:
List<Integer> list = Collections.synchronizedList(new ArrayList<>());
// Even list.get(0) and list.add(10) cannot run in parallel.
c) ConcurrentModificationException
Another major problem with traditional collections is that they fail fast during concurrent modification.
If one thread is iterating over a collection and another thread modifies it (adds or removes an element),
the iterator immediately throws a ConcurrentModificationException.
Example:
List<Integer> list = new ArrayList<>();
list.add(10); list.add(20); list.add(30);

for (Integer i : list) { // Iteration
    list.add(40);        // Modification by same or another thread
}
// => ConcurrentModificationException

This behavior makes traditional collections unsafe for concurrent iterations.


Non-Thread-Safe Collections:
-> These are the standard, general-purpose collection classes that are not safe to use concurrently without
external synchronization.
-> Best performance in single-threaded use.
-> Must be manually synchronized (e.g., using synchronized, lock, or mutex) if accessed by multiple threads.

Category	Common Interfaces	Typical Implementations
List	     List<T>	         ArrayList, LinkedList
Set	         Set<T>	             HashSet, TreeSet
Map	         Map<K,V>	         HashMap, TreeMap
Queue	     Queue<T>	         ArrayDeque


Synchronized (Thread-Safe via Locking) Collections:
-> These are wrapped or inherently synchronized versions of standard collections. Only one thread can
access the collection at a time.

Thread-safe via intrinsic or external locking:
-> Simpler, but may have contention bottlenecks under high concurrency.
Category	Common Interfaces	Typical Implementations
List	    List<T>	            Collections.synchronizedList(...), Vector
Map	        Map<K,V>	        Collections.synchronizedMap(...), Hashtable
Set	        Set<T>	            Collections.synchronizedSet(...)

ConcurrentHashMap:->
-> it is thread safe concurrent collection while normal HashMap is not thread safe.
-> in this map total bucket level lock is implemented instead of entire hashmap.the initial size of the
map object is 16 so 16 multiple thread are allowed to update the bucket simultaneously while any no of
thread can perform read operation.
-> hashmap stores data internally in bucket.
-> for each bucket a separate lock is maintained.
-> in hashtable to perform any operation thread required total map object lock but in the case of
concurrent hash map thread won't required total map object lock.thread required segment lock so
performance of the system will be improved.
-> if there are 16 bucket but only 8 are used then for every two buckets one lock will be maintained.

Conclusions:->
-> Underlying data structure is hash table.
-> concurrent hashmap allows concurrent read and thread-safe update operations.
-> to perform read operation thread won't require any lock but to perform update operation thread
requires lock but it is lock of only a particular part of map(Segment lock/bucket lock) instead of
total map.
-> concurrent update archived by internally dividing map into smaller portions which is defined by
concurrency level.
-> the default concurrency level is 16.
-> concurrent hash map allows any no of read operations but 16 update operations at a time by default.
-> null is not allowed for both keys and values.
-> while one thread iterating ,the other thread can perform update operations and concurrent hashmap
never throw concurrent modification exception.
